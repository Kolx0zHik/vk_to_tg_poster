# Журнал решений (ADR)

Формат: **Контекст → Решение → Альтернативы → Последствия**. Новые записи добавляются снизу, номера не
переиспользуются. Решения, принятые вместе с владельцем в сессии 2026-09-14…16, помечены 👤.

---

## ADR-001. Состояние — JSON-файлы, без базы данных

- **Контекст:** сервис разворачивается одним контейнером у одного владельца, объёмы — десятки постов в час.
- **Решение:** состояние и конфиг живут в `data/` (YAML + JSON), монтируются volume; БД не вводим.
- **Альтернативы:** SQLite/Postgres — надёжнее при параллельных записях, но добавляют схему, миграции и вес образа.
- **Последствия:** простое резервное копирование и правка руками; запись обязана быть атомарной (`tmp` + `fsync` + `os.replace`);
  два процесса делят файлы, поэтому у каждого файла ровно один владелец (см. ADR-009).

## ADR-002. Учёт постов статусами и baseline вместо `last_seen`

- **Контекст:** старая схема с единственным `last_seen` теряла посты: сбой публикации сдвигал отметку, а
  при перезапуске батч мог быть перезаписан (реальные потери фиксировались в логах).
- **Решение:** кэш schema v2 — записи постов со статусами `pending/published/skipped/dead` + `attempts`,
  плюс per-community `baseline` «всё ≤ (date, post_id) обработано».
- **Альтернативы:** хранить только `last_seen` (теряет посты); внешняя очередь (лишняя инфраструктура).
- **Последствия:** упавшие посты повторяются (до 5 попыток), бэклог публикуется порциями, рестарт не теряет
  прогресс; цена — рост файла состояния и обязательная миграция старой схемы с бэкапом `cache.json.v1.bak`.

## ADR-003. Дедупликация по оригиналу репоста, глобально

- **Контекст:** сообщества часто репостят один и тот же пост друг у друга.
- **Решение:** ключ = `owner_id_post_id` оригинала из `copy_history`, хранится глобально, не по сообществам.
- **Альтернативы:** ключ по паре (сообщество, пост) — допускает повторы одного поста в канале.
- **Последствия:** один и тот же пост никогда не уедет дважды, даже из разных сообществ; обратная сторона —
  осознанно теряем «вторую публикацию» (см. STATE баг №7, при необходимости — флажок в ROADMAP).

## ADR-004. Кэш owner id и троттлинг VK

- **Контекст:** каждый цикл резолвил screen name заново, VK отвечал `error_code 6` (слишком много запросов),
  часть сообществ не обрабатывалась.
- **Решение:** локальный парсер ссылок (`src/vk_ids.py`) → кэш `owner_ids` (TTL 30 дней) → только затем VK;
  интервал между запросами 0.34 с, ретраи на коды 6/9/10 и сетевые ошибки с экспоненциальной задержкой.
- **Альтернативы:** увеличить паузу целиком (медленнее для нескольких сообществ); отказаться от ретраев.
- **Последствия:** один resolve на сообщество вместо каждого цикла (в логах: было 806 сбоев resolve, 1172 «too many requests»),
  сбои VK больше не приводят к потере постов в этом же запуске.

## ADR-005. Маскирование секретов в логах и API

- **Контекст:** аудит логов нашёл VK-токен в открытом виде в текстах ошибок и в `/api/logs`.
- **Решение:** `redact_secrets` + форматтеры (`RedactingFormatter`, `CompactFileFormatter`), санитайз ошибок
  VK-клиента до логирования, маскирование в ответе `/api/logs`.
- **Альтернативы:** не логировать ошибки вовсе (потеряем диагностику); чистить только на выдаче (в файле остаётся).
- **Последствия:** секреты не попадают в новые записи; файл, писавшийся до 1.0.0, остался «грязным» —
  вопрос ротации токена за владельцем.

## ADR-006. Единая нормализация VK-ссылок и атомарный конфиг

- **Контекст:** в конфиг попадали `https://vk.ru/club123`, `club123`, `-123`, `@name`; ручное редактирование
  ломало формат; панель сохраняла screen name вместо числового id.
- **Решение:** один модуль `src/vk_ids.py` (`normalize_community_key`, `parse_owner_id`, `normalize_display_id`),
  запись конфига атомарная, ошибки разбора — `ConfigError`; `POST /api/config` нормализует id и ловит дубли.
- **Альтернативы:** нормализовать только в пайплайне (в конфиге остаётся мусор); валидировать строго по regex.
- **Последствия:** в конфиге оседает числовой id (или screen name, если иначе нельзя), панель и планировщик
  понимают одинаковые записи; загрузка из YAML перестала падать сырыми исключениями.

## ADR-007. Фото загружаем файлом, а не отдаём URL

- **Контекст:** Telegram не мог забрать часть фото с VK-URL (46 падений `sendMediaGroup`, 78 `sendPhoto` в логах).
- **Решение:** скачивать фото (`MAX_PHOTO_BYTES=10 МБ`) и отправлять multipart, при неудаче скачивания —
  откат на передачу по URL.
- **Альтернативы:** всегда по URL (текущие падения); всегда файлом без отката (падаем на больших фото).
- **Последствия:** исчезли сбои «Telegram не смог скачать», вырос трафик и время цикла; для видео/аудио
  такого решения пока нет (см. STATE баг №4).

## ADR-008. 👤 Панель групп: «список + настройки», без чекбоксов и без ID

- **Контекст:** старая панель групп держала на экране числовой ID, чекбоксы типов и дублировала подпись
  «на паузе» (свитч + бейдж); владелец просил переделать «целиком», ID не показывать вообще.
- **Решение:** master-detail (слева поиск и список, справа настройки выбранного), типы контента — иконки-переключатели,
  статус — сегмент «Активно/На паузе» (индикатор один: янтарная точка на аватаре), ID не отображается нигде,
  название в шапке — ссылка на сообщество, редактирование названия из панели убрано.
- **Альтернативы:** плитки, плотные строки, аккордеон, матрица (все 5 макетов показаны владельцу) — выбрана
  master-detail как единственная, куда нормально встают дозаливка и автосохранение.
- **Последствия:** список отдаёт больше места, чем строки; добавление/удаление сообщества = единственный способ
  исправить ссылку (правка id из панели убрана); список без второй строки — название остаётся единственным
  ориентиром.

## ADR-009. Заявки на дозаливку — отдельным файлом `backfill.json`

- **Контекст:** дозаливку и «только новые» надо передавать из веба в планировщик, а `cache.json` непрерывно
  перезаписывается планировщиком.
- **Решение:** веб пишет `data/backfill.json` (атомарно, рядом с `cache_file`), планировщик превращает заявку
  в baseline при следующем цикле и удаляет её; при сбое VK заявка остаётся.
- **Альтернативы:** писать baseline прямо в `cache.json` из веба — риск откатить прогресс и повторно
  опубликовать посты; хранить политику в конфиге — потребовало бы менять схему и «одноразовый» флаг.
- **Последствия:** у каждого файла один владелец; окно гонки минимально (заявки создаёт человек, TTL 30 дней),
  повторное применение baseline идемпотентно.

## ADR-010. 👤 Семантика паузы: возобновление «только с текущего места»

- **Контекст:** после паузы накопленный бэклог либо вываливался в канал, либо терялся из-за лимита `posts_limit`.
- **Решение:** снятие с паузы отправляет заявку `mode=none`, baseline ставится на самый свежий пост —
  публикуются только посты, появившиеся после включения.
- **Альтернативы:** догонять всё накопленное (спам в канале); не делать ничего (потеря постов из-за лимита).
- **Последствия:** предсказуемое поведение и один и тот же механизм для «только новые» при добавлении;
  осознанно пропускаем всё, что вышло за время паузы.

## ADR-011. 👤 Модалка добавления сохраняет сразу, без общей кнопки

- **Контекст:** добавление сообщества требовало отдельного нажатия «Сохранить» в другой карточке, что путало.
- **Решение:** добавление — модальное окно в стиле «Токенов»: живая проверка ссылки, пресеты количества
  кнопками (посты 3/7/10/20/50, дни 1/2/3/5/7), выбор типов контента; при подтверждении сразу идут
  `POST /api/config` и `POST /api/backfill`.
- **Альтернативы:** оставить ввод inline в панели (не помещается), либо копить состояние до общего Save (путаница).
- **Последствия:** добавление стало атомарным для пользователя; общая кнопка «Сохранить» осталась для
  настроек, статуса и типов контента.

## ADR-012. 👤 Ветки, образы и версии: `test` → `latest` → тег

- **Контекст:** правки уходили напрямую в `main`, владелец не успевал проверить их на стенде.
- **Решение:** любая работа — в ветке (`feature/**`, `fixes/**`) → образ `:test` + `:sha-<short>` → проверка
  владельцем на тестовом стенде → только затем merge в `main` (`:latest`) и при необходимости тег `vX.Y.Z`.
- **Альтернативы:** работать в `main` (уже приводило к преждевременным релизам).
- **Последствия:** процесс медленнее, но прод не получает непроверенное; версия в `VERSION` поднимается на
  каждый шаг (сейчас 1.1.8), теги `v1.0.0`, `v1.1.0`, `v1.1.1` уже есть.

## ADR-013. 👤 Раскладка страницы: карточки друг под другом

- **Контекст:** две колонки (настройки | группы) на телефоне и на ноутбуке выглядели тесно.
- **Решение:** блоки идут вертикально во всю ширину; внутри карточек — адаптивные сетки; на узких экранах
  подвал карточки складывается, кнопка занимает всю ширину, сводка панели переносится на отдельную строку.
- **Альтернативы:** оставить сетку 2×N (отвергнуто владельцем).
- **Последствия:** страница длиннее по вертикали, зато нет горизонтального скролла на 390px (проверено численно);
  редизайн самого блока настроек отложен — см. [ROADMAP.md](./ROADMAP.md).

## ADR-014. 👤 Никаких секретов и прод-доступа у агентов

- **Контекст:** в проекте уже был инцидент с токеном в логах и преждевременными пушами в `main`.
- **Решение:** агенты не пушат в `main`, не публикуют образы, не трогают прод и реальные `data/`
  без явного указания владельца; секреты не логируются и не коммитятся; проверочные запуски — на отдельном
  конфиге в `/tmp`.
- **Альтернативы:** разрешить агентам «финальный» шаг по своему усмотрению — приводит к непроверенным релизам.
- **Последствия:** финальные шаги делает владелец; правила зафиксированы в [AGENTS.md](./AGENTS.md).

## ADR-015. 👤 Один предел 1024 и одна пометка для caption и текста

- **Контекст:** посты VK длиннее 4096 символов роняли `sendMessage` (ошибка Telegram → `pending` → `dead`),
  при этом caption видео/аудио вообще не резались до 1024; обрезка была только у одиночного фото.
- **Решение:** везде, включая обычные сообщения, действует тот же предел и та же пометка, что у caption:
  `_truncate_text` режет до `CAPTION_LIMIT=1024` по границам абзац → строка → предложение → слово и
  добавляет «Продолжение текста читайте в источнике». Все текстовые сообщения уходят в HTML-режиме
  (`_escape_html` у вызывающего), поэтому смещение отводится назад `_safe_offset`, чтобы не разорвать
  сущность или тег. У видео место под статистику резервируется заранее.
- **Альтернативы:** отдельный лимит 4096 для сообщений (проверен на стенде — владелец счёл слишком длинным);
  разбиение на несколько сообщений (тоже отклонено: лента из нескольких сообщений не понравилась);
  гибрид «N частей + обрезка»; всегда анонс + ссылка.
- **Последствия:** один пост всегда даёт фиксированное число сообщений и одинаковую пометку везде; часть
  длинного текста теряется в пользу ссылки на источник; лимит считается по длине HTML-полезной нагрузки
  (консервативнее видимых символов); дубли при частичном сбое (баг №3) не размножаются на несколько
  сообщений.

## ADR-016. Удаление сообщества сохраняется сразу, состояние в кэше остаётся

- **Контекст:** удаление в панели раньше меняло только локальное состояние JS и не сохранялось в конфиг,
  пока пользователь отдельно не нажмёт общий «Сохранить»; после перезагрузки страницы сообщество возвращалось.
- **Решение:** отдельный эндпоинт `DELETE /api/community/{id}`: веб читает конфиг, удаляет запись по
  нормализованному id, валидирует результат и атомарно сохраняет; в интерфейсе — модалка подтверждения.
  Записи сообщества в `cache.json` не трогаются (`_cleanup_cache` остаётся заглушкой).
- **Альтернативы:** удалять только через общий «Сохранить» (текущее поведение — теряется); чистить
  `cache.json` из веба (нарушает ADR-009: кэш принадлежит планировщику, риск откатить прогресс).
- **Последствия:** удаление необратимо для конфига, но повторное добавление продолжает с сохранённого
  baseline — старые посты заново не уезжают; «удалить и забыть» с очисткой кэша остаётся в
  [ROADMAP.md](./ROADMAP.md) (баг №9).

## ADR-017. 👤 Все секреты — в `.env`, из `config.yaml` убраны

- **Контекст:** VK-токен и Telegram bot token лежали в `config.yaml` (с env-перекрытием) и правились из
  модалки «Токены»; конфиг монтируется volume и попадает в бэкапы вместе с секретами.
- **Решение:** секреты (`VK_API_TOKEN`, `TELEGRAM_BOT_TOKEN`, `LLM_API_KEY`) живут только в `.env` рядом с
  `CONFIG_PATH` (в докере — монтируемый `data/`). `src/envfile.py` читает простые `KEY=VALUE` строки без
  новых зависимостей, явные env-переменные важнее файла. Токены из YAML не читаются вообще; модалка
  «Токены» удалена, `telegram.channel_id` перенесён в «Основные настройки».
- **Альтернативы:** оставить токены в YAML и маскировать (текущий риск утечки через volume/бэкап); только
  `docker-compose env_file` (ломает локальный запуск из исходников); веб пишет `.env` сам (лишние права и
  сложность, перезапуск всё равно нужен).
- **Последствия:** смена секретов требует правки `.env` и перезапуска контейнера (веб их не редактирует);
  приложение стартует без токенов и просто пропускает публикацию с предупреждением; `.env.example`
  документирует ключи, сам `.env` — в `.gitignore`.

## ADR-018. 👤 Семантические дубли — до публикации, через LLM за флагом

- **Контекст:** владелец держал внешний n8n-флоу, который ловил семантические дубли уже в Telegram и
  удалял сообщение (`deleteMessage`) по вердикту LLM, сравнивая с историей за 4 дня. Это костыль:
  требует прав админа в канале, дубль успевает появиться, состояние живёт вне проекта.
- **Решение:** перенести проверку внутрь пайплайна, но **до** публикации. При
  `general.semantic_dedup.enabled` каждый новый пост с текстом сравнивается с пулом опубликованных постов
  за `window_days` (по умолчанию 4); вердикт «дубликат» → `skipped`, иначе публикуем. Провайдер —
  OpenAI-совместимый `/chat/completions` (`llm.base_url`, `llm.model`, `llm.prompt`, ключ `LLM_API_KEY`),
  интеграция — `src/dedup.py` на существующем `requests`. Системный промпт настраивается из панели; пустой
  `llm.prompt` означает встроенный `DEFAULT_SYSTEM_PROMPT`. Кандидаты и новый пост передаются модели в форме
  `{chat_id, message_id, date_unix, raw_text}`, где `chat_id` — Telegram-канал. Любая ошибка LLM — fail-open.

- **Альтернативы:** оставить n8n (внешняя зависимость, удаление после факта, два источника правды); post-hoc
  удаление внутри проекта (нужны права админа и хранение Telegram message id — отброшено); детерминированная
  эвристика вместо LLM (не ловит «тот же инфоповод другими словами» — отложено как возможный первый фильтр).
- **Последствия:** дубль не появляется в канале вообще, права админа и n8n не нужны; проверка выключена по
  умолчанию и включается из панели; кандидаты — опубликованные посты **всех** сообществ (владелец выбрал
  глобальный охват, как и у обычного дедупа); за корректность отвечает промпт, а ложное срабатывание
  приводит к пропуску поста, поэтому промпт консервативен, а тексты кандидатов хранятся ограниченное время.
