# План развития

Основано на состоянии 1.1.14 (ветка `feature/semantic-dedup`). Приоритеты — по влиянию на пользователя, а не по сложности.
Номера багов совпадают с таблицей в [STATE.md](./STATE.md). Статусы: `[ ]` не начато, `[~]` в работе, `[x]` сделано.

## Ближайшее (следующие 1–3 итерации)

- [x] Дозаливка при добавлении сообщества (none / N постов / D дней) и «только новые» при снятии с паузы.
- [x] Уборка репозитория: мёртвый `src/scheduler.py`, зависимость `apscheduler`, пустые `scripts/` и `.codex`, stray `poster.log`.
- [x] Документация приведена в актуальное состояние (README, ARCHITECTURE, STATE, ROADMAP, DECISIONS, CHANGELOG, AGENTS).
- [x] Удаление сообщества из панели сохраняется на сервере (`DELETE /api/community/{id}`, 1.1.13) с модалкой
      подтверждения.
- [ ] **Редизайн блока «Основные настройки».** Макеты готовы (4 варианта), решение отложено владельцем.
      Требования: блоки друг под другом во всю ширину; контролы не растянуты; на 390px нет горизонтального скролла.
- [x] **Обрезка длинных текстов (>4096)** для `sendMessage` (баг №2) — сделано в 1.1.10: везде, как у
      caption, один предел `CAPTION_LIMIT=1024` и пометка «Продолжение текста читайте в источнике».
      Варианты «разбить на несколько сообщений» и «отдельный лимит 4096» отклонены владельцем.
- [ ] **Разбиение альбомов >10 фото** на группы по 10 (баг №1).
- [ ] **Повторная отправка без дублей**: перед повтором проверять, что уже ушло (баг №3).
- [ ] Обновить прод владельцу: `docker compose pull && docker compose up -d`.

## Далекое / идеи

- [ ] Несколько Telegram-каналов и маршрутизация сообществ по каналам.
- [ ] Индивидуальное расписание на сообщество (сейчас одно общее — принципиальное ограничение).
- [ ] Метрики и статус пайплайна в веб-панели (сколько опубликовано, что в `pending`/`dead`).
- [ ] Ручная повторная публикация `dead`-постов из интерфейса.
- [ ] Интерактивный предпросмотр: «что уедет в канал» для выбранного сообщества.
- [ ] Опциональный второй бэкенд состояния (SQLite) — только если файлы станут узким местом;
      текущее решение «без БД» менять не планируется.

## Явно не планируется

- Отказ от файлового состояния и переезд в БД «просто потому что так правильнее».
- Второе расписание/планировщик (один cron на всё — осознанное ограничение).
- Автоматические коммиты/мержи от агентов без подтверждения владельца (см. [AGENTS.md](./AGENTS.md)).
